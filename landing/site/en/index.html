Why

headscale gives you the network. The rest is manual

headscale issues keys, keeps the netmap and enforces the policy. Managing it means the CLI and a policy.hujson file. That is fine for five nodes; past that you memorise tags, hope you got the ACL right, SSH into every node for a single route, and hear about a node being down from its user. NodeRoost is a management layer on top of the same headscale — it does not replace it and it does not proxy traffic.

Model

What makes something a server and something else a device

headscale knows nothing about this: to it every machine is just a node, all alike. The split into servers and devices is ours, and it lives in the panel's database. The idea is simple — a server is what you connect to, a device is what you connect from. And which one the panel thinks a machine is decides what rules you can write for it.

Server

You connect to it

  • This is what access gets opened to: a database, a hypervisor, the office router, a build machine.
  • Servers can be grouped into roles, so you grant the role instead of every machine one by one.
  • A server can hand out its local network or work as a gateway out to the internet.
  • The agent goes on servers — it picks up the routes you set in the panel.

Device

You connect from it

  • A laptop, a phone, a work computer — anything with a person sitting at it.
  • A device is given access to servers. Giving access to the device itself is not possible — that rule cannot be written.
  • Devices don't see each other: a colleague's laptop won't appear in the list, and typing its address by hand won't work either.
  • This is also where you allow exit gateways — which ones the person can switch on.
  • The panel works out which is which. Roles, an approved subnet or gateway mode mean a server. None of that means a device.
  • Got it wrong? Set it by hand. On the node's card you can pin the type or hand it back to the automatic choice.
  • The panel trusts you, not the node. A node can announce “I route 192.168.0.0/24”. If the panel took that at face value, anyone who got onto someone's laptop would need one command to make it a “server” — and that laptop would join “all servers”, stop hiding from other devices and inherit everything granted to servers. So only what you confirmed counts: you assign the roles, you approve the subnets.

Use cases

What people build with it

None of this needs a public IP on the client, a port forward on the router or a reverse tunnel — the node keeps the connection to the control server itself.

Two LANs, no public addresses

192.168.10.0/24 ─ node-a ══ node-b ─ 192.168.50.0/24

The office and the warehouse start seeing each other's networks. Put one node on each side, it advertises its subnet, you approve it — then rules decide who may cross. Neither side needs a static address from its ISP.

A work machine behind someone else's NAT

laptop ══ work-pc : 3389

Carrier-grade NAT, a router you don't own, nobody to ask for a port forward. Put a node on that machine and it shows up on the network. You open access to your laptop only, on one port only — no TeamViewer, no reverse tunnel.

Admin panels and databases with no open ports

postgres · kube-apiserver · ipmi · admin UIs

The database, the IPMI board, the cluster API and the router's web UI live on tailnet addresses. Nothing is published, no bastion host needed, and you grant a port rather than the whole machine.

A contractor gets exactly what they need

contractor → role prod-db → 5432

You grant a role, not a machine. Add another server to that role and the contractor picks it up automatically. The job ends — you delete their device and the access is gone everywhere at once.

Internet through the node you pick

device → gw-de → internet

Mark a server as a gateway and say who may use it. People switch it on themselves in Tailscale, but the list they see contains only what you allowed.

A server's whole traffic through another server

app-01 ══ gw-nl → internet + inbound on its own IP

Sometimes you need a machine's outbound traffic to leave from another country for a while. It is one switch, and the server does not disappear: SSH and the site on its public address keep working. The panel makes sure replies leave the way the request came in.

A service that allows one address only

laptop → api.example via edge-1

A partner API, a payment gateway, an admin panel with an IP allowlist. You say: reach this address through that server — and the requests arrive from its address. Everything else goes as before.

Home NAS, cameras, Home Assistant

phone ══ nas · camera · homeassistant

No public IP, no dynamic DNS, no port forwarding on the router. Put a node on the home server and reach it from your phone anywhere exactly as you would from the sofa.

Server to server

ci-runner → db-fra-1 : 5432

The runner writes to the database, the backup job ships to storage, the app talks to the next data centre. This used to be an IP allowlist on a firewall that broke on every migration. Now it is one rule in the panel.

Not everything goes into the tunnel

work addresses → via the network · the rest → direct

A normal VPN swallows all your traffic. Here the laptop reaches the internet directly and fast, and only what you listed goes through the network: office subnets, specific services, individual addresses.

The ISP changed — nothing broke

100.64.0.7 — the address stays

You moved to another data centre, the provider handed out a new address, the machine went from the office to someone's home. On the tailnet it keeps its address and its name, so rules, scripts and bookmarks need no editing.

Instead of mailing out VPN configs

key → one command → node in the list

No .ovpn attachments. A person gets a single-use key and one command for their OS — a minute later they are on the network. Revoking means deleting a device, not reissuing configs for everyone else.

Architecture

The panel controls the network without sitting in the data path

The headscale management API is never exposed: the panel reaches it over an internal Docker network. Only the node-facing surface of the control server is published — the part Tailscale clients actually need.

  • The panel never sees user traffic. It distributes policy and configuration; packets travel between nodes directly over WireGuard.
  • The agent is a separate channel. headscale has no “panel → node” path, so the node fetches its routes and exit mode by token and applies them locally, confirming with a hash.
  • The policy is generated as a whole. Rules, roles, gateways and directions become one HuJSON document; it is validated, applied, and rolled back to the last working version if headscale rejects it.
  • The panel's database is only the panel's. Tailnet state stays in headscale rather than being mirrored.

Install

Docker Compose next to headscale

The panel, Postgres and headscale itself come up from one file. A reverse proxy terminates TLS and keeps the panel behind an address allowlist.

# 1. get the repository
git clone https://github.com/mihsergeev/NodeRoost.git
cd NodeRoost

# 2. domains, secrets, allowlisted addresses
cp .env.example .env && $EDITOR .env

# 3. bring it up
docker compose up -d

# 4. enrol a node — the panel hands you this command
curl -fsSL https://control.example.com/agent/<token>/setup | sh

Security

Invariants live in the code, not in the UI

The panel runs a VPN, and a rule can arrive from an API call as easily as from a click. So the checks sit in the policy engine.

  • A device never becomes a target. Not by selection, not by an address supplied in a request.
  • A node cannot promote itself. Its class and tags come from what the administrator confirmed, not from what the node announced about itself.
  • Sign-in. JWT and TOTP, attempt limits, an audit log; the panel refuses to start with a weak secret or a default password.
  • Builds. Dependencies pinned with hash verification, base images pinned by digest, tests and a dependency audit on every commit.
