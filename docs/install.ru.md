# Установка NodeRoost

Инструкция проверена целиком: на чистой Ubuntu поднята панель, к ней подключены
три машины (два сервера и устройство), проверены доступы, изоляция, подсети,
шлюз выхода, направления, бэкапы и алерты. Всё, что ниже, — то, что выполнялось
вживую, а не по памяти.

[English version](install.md)

---

## Что понадобится

| | |
|---|---|
| Сервер | Ubuntu или Debian, 1 vCPU и 1 ГБ памяти хватает. Нужен root (sudo). |
| Порты наружу | **80** и **443** (TCP) — сертификаты и работа, **3478** (UDP) — STUN встроенного DERP, помогает нодам за NAT соединяться напрямую. |
| Два домена | Один для панели, второй для control-сервера. Оба должны указывать A-записью на этот сервер. |

**Домена нет?** Возьмите [sslip.io](https://sslip.io) — он резолвит имя вида
`panel.203-0-113-10.sslip.io` в адрес `203.0.113.10` без всякой регистрации.
Именно на нём проверялась эта инструкция. Для постоянной установки лучше свой
домен: имя control-сервера ноды запоминают у себя, и менять его потом дорого.

**Почему доменов два.** headscale отдаёт на одном порту и то, к чему
подключаются ноды (это обязано быть публичным), и управляющий API (это обязано
быть закрыто). Панель ходит в API по внутренней сети Docker, а наружу от
control-сервера остаётся только узловой контур.

---

## Установка одной командой

```bash
curl -fsSL https://raw.githubusercontent.com/mihsergeev/NodeRoost/main/ops/install.sh \
  | sudo bash -s -- \
      --panel-domain panel.example.com \
      --hs-domain hs.example.com
```

Скрипт поставит Docker, скачает NodeRoost в `/opt/noderoost`, сгенерирует
пароли, поднимет панель, headscale и Caddy, получит сертификаты и напечатает
логин с паролем:

```
  NodeRoost is installed.

  Panel:           https://panel.example.com
  Control server:  https://hs.example.com
  Login:           admin
  Password:        npMBKFqLc5aiDVsmuUV8
```

Сертификат Let's Encrypt выдаётся при первом обращении — если страница не
открылась сразу, подождите полминуты и обновите.

Скрипт **идемпотентный**: повторный запуск обновит код и домены, но не тронет
пароли, базу и выданные сертификаты.

### Параметры

| Параметр | Зачем |
|---|---|
| `--panel-domain ДОМЕН` | Имя панели. Обязательный. |
| `--hs-domain ДОМЕН` | Имя control-сервера. Обязательный. |
| `--allow-ips "СПИСОК"` | С каких адресов пускать в панель, через пробел. По умолчанию отовсюду. |
| `--ufw` | Настроить фаервол: закрыть всё, кроме SSH, 80, 443 и 3478/udp. |
| `--dir ПУТЬ` | Куда ставить. По умолчанию `/opt/noderoost`. |
| `--version ТЕГ` | Версия образов. По умолчанию последний релиз. |
| `--build` | Собрать образы из исходников вместо готовых. |
| `--public-ip АДРЕС` | Внешний адрес для встроенного DERP, если автоопределение ошиблось. |

Пример с ограничением доступа и фаерволом:

```bash
curl -fsSL https://raw.githubusercontent.com/mihsergeev/NodeRoost/main/ops/install.sh \
  | sudo bash -s -- \
      --panel-domain panel.example.com \
      --hs-domain hs.example.com \
      --allow-ips "203.0.113.10 198.51.100.0/24" \
      --ufw
```

## Кого пускать в панель

По умолчанию панель открыта всем — чтобы первая установка просто заработала.
Как только вошли и сменили пароль, сузьте список: панель управляет всей сетью,
и держать её открытой миру незачем.

```bash
cd /opt/noderoost
sudo nano .env          # NODEROOST_ALLOW_IPS=203.0.113.10 198.51.100.0/24
sudo docker compose up -d caddy
```

Адреса перечисляются через пробел, годятся и одиночные, и подсети. Проверить
просто: с чужого адреса панель перестанет отвечать (соединение оборвётся), а
control-сервер продолжит работать — ноды это не заденет.

Если оставить переменную пустой, панель закроется для всех (подставится
`127.0.0.1`). Это сделано намеренно: забытая настройка не должна открывать
админку миру.

## Фаервол (по желанию, но стоит)

`--ufw` при установке настроит всё сам. Вручную:

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw route allow 80/tcp
sudo ufw route allow 443/tcp
sudo ufw route allow 3478/udp
sudo ufw enable
```

**Важно про `route allow`.** Порты, опубликованные Docker, проходят через цепочку
FORWARD, а не INPUT — обычного `ufw allow 443/tcp` для них недостаточно, правило
просто не сработает. Нужен именно `ufw route allow`.

Закрывать 3478/udp можно, но тогда ноды за NAT чаще будут соединяться через
ретранслятор, а не напрямую — медленнее.

## Подключение машин

В панели: **Серверы → Добавить сервер** (или **Устройства → Добавить
устройство**). Укажите имя, выберите ОС — панель покажет готовый скрипт с
одноразовым ключом. Скопируйте его и выполните на машине под root:

```bash
sudo sh -c "вставленный скрипт"
```

Скрипт ставит Tailscale нужной версии (сначала из локального мирора панели,
если недоступен — с официального сайта) и подключает машину. Через несколько
секунд она появится в списке: статус в окне обновляется сам, ждать не нужно.

Ключ одноразовый и живёт час. Скрипт первой же строкой отключает запись в
историю shell, чтобы ключ туда не попал.

**Серверы и устройства.** Разделение придумано панелью, в headscale его нет.
К серверу можно открыть доступ, к устройству — нельзя: устройства не видят друг
друга вообще. Тип определяется автоматически (есть роли, одобренная подсеть или
режим шлюза — сервер), но его можно задать руками в карточке ноды.

**Агент.** Нужен, если вы хотите управлять из панели тем, что нода анонсирует:
подсетями, режимом выхода, направлениями. Команду установки даёт карточка ноды,
раздел «Агент». Без него нода работает, просто маршруты придётся задавать на ней
самой.

## Что дальше

- **Смените пароль** и включите второй фактор: ⚙ → Сменить пароль, ⚙ → Двухфакторный вход.
- **Проверьте доступы.** Сразу после установки не разрешено ничего: пока не
  выдали правило, ноды друг друга не видят.
- **Настройте алерты** (⚙ → Алерты): Telegram или вебхук. Приходят при падении
  сервера и истечении ключа.
- **Обращайтесь с бэкапом как с приватным ключом.** В архиве секрет второго
  фактора, хеш пароля администратора, токены агентов и собственные ключи headscale —
  см. [SECURITY.md](../SECURITY.md).
- **Бэкапы** идут сами раз в сутки (⚙ → Бэкапы). Архив — это консистентный
  снимок базы headscale и настроек панели; восстановление описано в
  `ops/restore.sh`. Восстановить можно и на другой машине: скрипт сам выпишет
  панели новый ключ к поднятой из архива базе headscale.
- **Сторож** уже стоит: `/lib65/noderoost/panel-watchdog.sh` раз в пять минут
  сверяет пульс панели и, если та замолчала, шлёт тревогу сам — своими руками,
  мимо панели. Иначе о смерти панели сообщать было бы некому.

## Установка без скрипта

Скрипт ничего волшебного не делает, всё то же руками:

```bash
git clone https://github.com/mihsergeev/NodeRoost.git /opt/noderoost
cd /opt/noderoost
cp .env.example .env
# заполнить: домены, NODEROOST_ALLOW_IPS, пароли (openssl rand -hex 32),
# NODEROOST_VERSION, COMPOSE_FILE=compose.yml:compose.tls.yml

mkdir -p data/headscale/config
sed -e "s|^server_url:.*|server_url: https://hs.example.com|" \
    -e "s|^\( *ipv4: *\)[0-9.]*|\1203.0.113.10|" \
    deploy/headscale/config.example.yaml > data/headscale/config/config.yaml

docker compose up -d
# панель поднимется и без ключа к headscale — и прямо скажет об этом
docker compose exec headscale headscale apikeys create --expiration 3650d
# ключ вписать в .env → NODEROOST_HEADSCALE_API_KEY
docker compose up -d backend
```

**Свой обратный прокси вместо Caddy.** Уберите `compose.tls.yml` из
`COMPOSE_FILE` — фронтенд снова опубликует порт из `NODEROOST_BIND`
(по умолчанию `127.0.0.1:8080`), проксируйте на него. Для домена
control-сервера повторите правила из `deploy/Caddyfile`: `/api/v1*` и
`/swagger*` → 404, `/pkgs/*` и `/agent/*` → фронтенд, остальное → `headscale:8080`.
Для caddy-docker-proxy готовый оверрей уже есть: `compose.caddy.yml`.

## Сертификаты для имён внутри сети

Сервис внутри сети хочется открывать по `https://` без предупреждений браузера, а
обычный путь к сертификату упирается в то, что имя наружу не смотрит: Let's
Encrypt некуда прийти с проверкой. Панель решает это за вас — и без API-ключей
DNS-хостинга, и без плагинов к прокси.

**Нужна одна DNS-запись. Один раз, любым хостингом:**

```
*.int.example.com   A   <публичный IP панели>
```

Дальше в `.env` панели:

```
NODEROOST_CERT_DOMAIN=*.int.example.com
```

и `docker compose up -d` — чтобы обратный прокси подхватил новый блок. Всё.

Теперь в разделе **DNS** у любого имени, ведущего на ноду, есть галочка с замком.
Ставите — и через минуту у сервиса есть сертификат:

1. Панель заказывает его у Let's Encrypt. Проверка приходит по 80-му порту на
   само имя — та самая wildcard-запись приводит её к панели, и панель отвечает.
2. Ключ генерит **сама нода** (нужен `openssl`) и никуда его не отдаёт: наверх
   уходит только запрос на подпись.
3. Агент кладёт `/etc/noderoost/certs/<имя>.crt` и `.key` и, если вы положили
   рядом `/lib65/noderoost-agent/cert-hook.sh`, запускает его — перезагрузить
   nginx, caddy или контейнер. Панель не присылает команд на выполнение: что
   именно перезапускать, решают на ноде.
4. За месяц до конца срока всё повторяется само.

О чём стоит знать заранее:

* **Имя попадёт в публичные CT-логи.** Let's Encrypt публикует каждый выданный
  сертификат: сам факт существования `nas.int.example.com` станет известен. Адрес
  и содержимое — нет.
* **80-й порт панели должен оставаться доступным** снаружи: по нему приходит и
  первая проверка, и все последующие продления.
* **Публично имя будет резолвиться в адрес панели.** Доступа это не даёт — на
  этих именах наружу отдаётся только путь проверки, всё остальное отвечает 404.
* Проверить выпуск, не тратя боевые попытки, можно на тестовом каталоге:
  `NODEROOST_ACME_DIRECTORY=https://acme-staging-v02.api.letsencrypt.org/directory`.
  Сертификаты оттуда браузер не признает, зато лимиты там мягкие.

## Если что-то не так

**Панель не открывается, сертификата нет.** Проверьте, что оба домена
резолвятся в этот сервер и что 80/443 доступны снаружи — Let's Encrypt
проверяет домен по 80 порту. Логи: `docker compose logs caddy --tail 30`.

**Заперты: потерян пароль, второй фактор или и то и другое.** Ссылки «забыли
пароль» в панели нет намеренно — она была бы входом. Восстановление идёт через
сервер, потому что у того, кто держит сервер, панель и так в руках:

```bash
cd /opt/noderoost
sed -i 's/^NODEROOST_ADMIN_PASSWORD_RESET=.*/NODEROOST_ADMIN_PASSWORD_RESET=1/' .env
sudo docker compose up -d backend      # вернёт пароль из NODEROOST_ADMIN_PASSWORD
                                       # и выключит второй фактор
sed -i 's/^NODEROOST_ADMIN_PASSWORD_RESET=.*/NODEROOST_ADMIN_PASSWORD_RESET=0/' .env
sudo docker compose up -d backend      # верните выключатель, иначе сброс повторится
```

Войдите паролем из `.env`, смените его и снова включите второй фактор. Все выданные
раньше сессии перестают работать, а сам сброс попадает в лог.

**Сертификат не выдаётся после нескольких переустановок.** В логах caddy —
`too many certificates (5) already issued for this exact set of identifiers`.
Let's Encrypt разрешает пять сертификатов на одно и то же имя за неделю; счётчик
сбросится сам, время указано в самой ошибке. Если ждать нельзя — поставьте
панель на другое имя. Каталог `data/caddy` между переустановками лучше сохранять:
в нём лежат уже выданные сертификаты, и повторная выдача не понадобится.

**Панель отвечает «нет соединения» с одного адреса и работает с другого.**
Сработал список адресов, смотрите `NODEROOST_ALLOW_IPS` в `.env`.

**Ноды не подключаются.** `curl https://hs.example.com/health` должен отдавать
200 откуда угодно. Если 404 — вы обращаетесь к домену панели, а не
control-сервера.

**headscale в рестарт-лупе.** `docker compose logs headscale --tail 5` покажет
причину: чаще всего это правка `config.yaml` руками. Рядом лежит `.bak`.

**Нода в списке есть, но маршруты не применяются.** Проверьте агента в карточке
ноды: он должен показывать «применено». Если «не установлен» — поставьте
командой оттуда же.

**Панель не видит headscale (`headscale: unconfigured`).** Не заполнен
`NODEROOST_HEADSCALE_API_KEY` в `.env`. Создать:
`docker compose exec headscale headscale apikeys create --expiration 3650d`.

**Имя внутри сети резолвится, но сайт не открывается: `ERR_HTTP2_PROTOCOL_ERROR`
(в curl — `Empty reply from server`).** Так выглядит сервис, который сам решает,
кого пускать по адресу клиента: соединение и TLS проходят, а запрос обрывается.
Если он живёт в Docker на этой ноде, до него доезжает **не** адрес из сети:
Tailscale по умолчанию подменяет адрес отправителя у трафика, который форвардит
дальше (в контейнер, в локальную сеть за нодой), — сервис видит адрес
docker-моста и не узнаёт своего. Проверяется на ноде так:

```bash
sudo iptables -t nat -S ts-postrouting     # есть MASQUERADE по метке 0x40000 — вот он
sudo tailscale set --snat-subnet-routes=false   # выключить подмену
```

Настройка живёт в самом Tailscale и переживает перезапуски, но её сбрасывает
`tailscale up --reset` — то есть повторное подключение ноды через панель. После
такого команду нужно повторить.

## Обновление и удаление

```bash
cd /opt/noderoost && sudo ops/update.sh
```

Скрипт забирает свежий код, переносит номер версии в `.env` и поднимает стек.
Одного `git pull` мало: теги образов панель берёт из `NODEROOST_VERSION` в
`.env`, а этот файл ваш и git его не трогает — команды отработают без ошибок, а
версия останется прежней.

Удалить всё вместе с данными:

```bash
cd /opt/noderoost && sudo docker compose down -v
sudo rm -rf /opt/noderoost /lib65/noderoost
sudo rm -f /etc/systemd/system/noderoost-hs-* && sudo systemctl daemon-reload
```
